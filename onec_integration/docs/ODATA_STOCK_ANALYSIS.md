# Анализ OData 1С УТ для ускорения чтения остатков

Дата проверки: 2026-07-28.

## Проверенный адрес

```text
http://pz-sql1/ut_dev/odata/standard.odata/
```

Сервис опубликован отдельно от COM-подключения и требует HTTP Basic-авторизацию учетной записью 1С. Учетные данные брать только из внешнего `.env`:

```text
C:\Users\dpd\Documents\Codex\1C_Diagnostics\.env
```

Пароль не выводить, не логировать и не переносить в проект.

## Что подтвердилось

- Без авторизации сервис отвечает `401`, значит endpoint живой и защищен.
- С авторизацией корневой список OData вернул `200 OK`; первый ответ занял около `12,4 с`, размер около `190 КБ`.
- `$metadata` вернул `200 OK`; ответ около `4,7 МБ`, время около `1,9 с` при первом замере.
- В метаданных найдено `1088` entity set.
- Опубликованы нужные объекты:
  - `Catalog_Номенклатура`;
  - `Catalog_Склады`;
  - `Catalog_ЕдиницыИзмерения`;
  - `AccumulationRegister_ТоварыНаСкладах`;
  - `AccumulationRegister_ПартииТоваровНаСкладах`;
  - `AccumulationRegister_ТоварыОрганизаций`.
- Для `AccumulationRegister_ТоварыНаСкладах` опубликована функция `Balance` с параметрами:
  - `Condition`;
  - `Dimensions`;
  - `Period`.

Это важно: OData может обращаться к виртуальной таблице остатков, а не только читать движения регистра.

## Практический замер

Проверочный сценарий для `УТ000011445` и склада `44 секция НЗП (незавершенное производство)`:

- поиск номенклатуры по `Catalog_Номенклатура` первым запросом: `6,2 с`;
- поиск склада по `Catalog_Склады`: `26 мс`;
- `AccumulationRegister_ТоварыНаСкладах/Balance(...)` по уже найденным GUID номенклатуры и склада: `15 мс`;
- результат остатка: `3.549`, что совпало с ранее полученным COM-helper ответом по основному регистру.

Повторные/кэшированные запросы:

- повторный поиск `УТ000011445` по коду: `18 мс`;
- пакетный поиск трех кодов в одном `$filter`: `19 мс`;
- поиск по части наименования `Заготовка 40х85х1020мм сталь 30ХГСА`: `244 мс`, найден код `УТ000023166`.

## Вывод по скорости

OData может ускорить работу с 1С в двух сценариях:

1. Холодный старт, когда COM-helper еще не поднят.
   OData не требует запуска `V83.COMConnector`; даже с первым тяжелым HTTP-запросом он должен быть быстрее холодного COM-старта около `50 с`.

2. Пакетные и повторные запросы при наличии кэша GUID.
   После того как GUID номенклатуры и складов найдены и закэшированы, `Balance` по остаткам отвечает за десятки миллисекунд.

Для одиночного оперативного вопроса при уже прогретом helper-сервере текущий COM-путь пока остается быстрее и надежнее: ранее `query_stock_server.cmd -Item "11445" -Warehouse "44"` отработал около `0,7 с` и сразу вернул код, наименование, склад и количество без отдельного кэша GUID.

## Рекомендация

Не заменять текущий COM-helper немедленно. Лучший следующий путь:

1. Оставить COM-helper основным оперативным каналом для точечных пользовательских запросов остатков.
2. Добавить OData как read-only альтернативу для:
   - холодного старта;
   - пакетных запросов до 30 строк;
   - синхронизации остатков по закрепленным складам;
   - обновления кэша номенклатуры и складов.
3. Реализовать локальный кэш соответствий:
   - `Code` / `Артикул` / нормализованный код -> `Ref_Key`, `Description`, единица;
   - склад по коду/наименованию -> `Ref_Key`.
4. Запрашивать остатки через:

```text
AccumulationRegister_ТоварыНаСкладах/Balance(Condition='<условие по GUID>',Dimensions='Номенклатура,Склад')
```

5. При ошибке OData, пустом кэше или сомнительном результате автоматически откатываться на COM-helper.

## Ограничения

- Стандартный OData возвращает остатки по GUID, поэтому для пользовательского ответа нужен справочный слой, который подтянет код, наименование и склад.
- Поиск по части наименования возможен, но для больших справочников его нужно ограничивать `$top`, `$select` и, по возможности, предварительным кэшем.
- Нельзя использовать OData для записи документов 1С в рамках текущего контура остатков.
- Контрольные регистры `ПартииТоваровНаСкладах` и `ТоварыОрганизаций` опубликованы, но их нужно включать только для сверки, как и в COM-helper.

## Решение для будущего внедрения

Для ПО "Заказ заготовок ЦМО" подготовить отдельный `OneCODataStockService` как второй read-only провайдер остатков. Он должен использовать OData в таком порядке:

1. Проверить доступность `http://pz-sql1/ut_dev/odata/standard.odata/`.
2. Загрузить/обновить кэш складов и номенклатуры.
3. Для закрепленных групп "Склад" и "НЗП/ЦМО" получить остатки через `Balance`.
4. Сохранить результат в тот же `StockSnapshot`, который сейчас заполняет COM-синхронизация.
5. При сбое вернуться к текущему Python/COM `sync_stock_sections.py`.

## Статус внедрения 2026-07-28

- Добавлен read-only OData-скрипт `onec_integration/tools/sync_stock_sections_odata.py`; `OneCStockSyncService` запускает его первым и сохраняет успешный результат в обычный `StockSnapshot`.
- Для защиты пользователя от долгого ожидания OData-путь ограничен 20 секундами в WPF и при ошибке автоматически переходит на COM.
- При живом полном прогоне выявлены ограничения стандартного OData УТ: фильтрация `Catalog_Склады` по `Description` в `$filter` запрещена сервером, а полный `Balance` по складу нестабилен без дополнительного кэша/точечных условий. В скрипте поиск складов переведен на локальный выбор из закэшированного списка, но COM fallback остается обязательным.
- COM fallback ускорен: `sync_stock_sections.py` теперь выполняет 2 пакетных запроса по группам складов вместо запроса по каждой секции. Живой read-only прогон дал `7770` строк без ошибок примерно за `31` секунду на холодном старте.
