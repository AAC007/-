# AGENTS.md

## Назначение проекта

Проект "Заказ заготовок для ЦМО" автоматизирует определение того, какие материалы и заготовки нужно закупить и к какой дате, исходя из трех источников:

- библиотеки деталей и соответствующих им заготовок;
- текущей производственной потребности;
- остатков склада и НЗП из выгрузок 1С.

Приложение должно быть готово к постоянному развитию, накоплению производственной истории и работе с десятками тысяч деталей. При доработках нужно беречь масштабируемость, проверяемость расчетов и воспроизводимость импортов из Excel.

## Обязательные проектные документы

Каждый агент, работающий в этом репозитории, обязан читать и поддерживать:

- `AGENTS.md` - правила работы агентов и ключевые договоренности проекта.
- `PROJECT_CONTEXT.md` - бизнес-контекст, архитектура, доменная модель и текущие возможности.
- `SESSION_HANDOFF.md` - актуальное состояние последней сессии, нерешенные вопросы, следующие шаги.
- `VERSION.md` - журнал пользовательски значимых изменений и опубликованных сборок.

Перед изменением кода сначала прочитай эти файлы. После значимой доработки обнови `PROJECT_CONTEXT.md`, `SESSION_HANDOFF.md` и при необходимости `VERSION.md`. Если решение меняет правила работы агентов, обнови также `AGENTS.md`.

## Текущее приложение

Репозиторий содержит Windows WPF-приложение на .NET 8:

- `BlankDemandPlanner.Core` - сущности, enum-типы, интерфейсы и DTO/records.
- `BlankDemandPlanner.Data` - EF Core контекст, SQLite-схема, миграции, индексы и история изменений справочных сущностей.
- `BlankDemandPlanner.Services` - бизнес-логика: нормализация заготовок, проверка И-012, расчет закупочной потребности, конвертация единиц, поиск дублей.
- `BlankDemandPlanner.Infrastructure` - импорт Excel/1С/ПП/производственной библиотеки, экспорт отчетов Excel, резервные копии.
- `BlankDemandPlanner.UI` - WPF UI на MVVM с `CommunityToolkit.Mvvm`.
- `BlankDemandPlanner.Tests` - xUnit/FluentAssertions тесты доменных сервисов, импортов и ViewModel.

Основная пользовательская база приложения хранится в SQLite в `Данные для работы\BlankDemandPlanner.db` внутри рабочего каталога проекта, чтобы ручные правки библиотеки и НСИ сохранялись между обновлениями ПО. При первом запуске после перехода база копируется из старого `%LOCALAPPDATA%\BlankDemandPlanner\BlankDemandPlanner.db`, если новая еще не создана. Логи пишутся в `%LOCALAPPDATA%\BlankDemandPlanner\Logs`; резервные копии - в `%LOCALAPPDATA%\BlankDemandPlanner\Backups`.

## Ключевые бизнес-правила

- IPS - основной идентификатор изготавливаемой детали.
- УТ/1С-код - основной идентификатор складской/номенклатурной позиции заготовки.
- Связь `Part -> CanonicalBlank` задает норму расхода заготовки на деталь.
- У детали может быть несколько активных связей, но только одна активная основная связь.
- Расчет берет последнюю партию потребности и последний снимок склада, если явно не передан другой снимок.
- Заявка должна отображать список деталей и соответствующих заготовок со сроками потребности.
- На первом этапе расчетная дата закупки считается как `дата потребности - 30 дней`; позже срок должен браться из библиотеки данных/вкладки расчетных сроков изготовления и поставки.
- Остатки склада вычитаются по алиасам заготовок 1С.
- Строки остатков 1С, где код совпадает с IPS детали из потребности и единица измерения `шт`, трактуются как НЗП. НЗП вычитается из количества деталей до расчета потребности в заготовках.
- Для сопоставления деталей приоритет имеет IPS, для сопоставления заготовок - УТ/1С-код.
- Длинномерные заготовки по умолчанию должны работать в `пог. м`; штучные, покупные, литые и листовые позиции - по фактической единице, если нет отдельного правила.
- Несовместимые единицы измерения не должны молча пересчитываться. Сейчас пересчет разрешен только при полном совпадении единиц.
- Повторный импорт того же файла потребности должен обновлять существующую партию, а не создавать дубль.

## Оперативные запросы остатков 1С

Если пользователь спрашивает текущий остаток конкретной детали/номенклатуры в 1С УТ, сначала используй прогретый read-only helper-сервер, а не Excel и не повторное обследование метаданных:

```powershell
Invoke-RestMethod -Uri "http://127.0.0.1:8765/health"
.\onec_integration\start_stock_lookup_server.cmd
.\onec_integration\query_stock_server.cmd -Item "<код или часть наименования>" -Warehouse "<секция или склад>"
```

Если helper-сервер не запущен, первый старт может занять около 50 секунд на открытие COM-соединения. После прогрева запросы должны идти заметно быстрее, так как COM-подключение уже открыто. Прямой cold-start fallback:

```powershell
.\onec_integration\lookup_1c_stock.cmd "<код или часть наименования>" "<секция или склад>"
```

Целевой регламент скорости: один запрос или пакет до 30 строк должен готовиться максимально коротким путем, ориентир - до 30 секунд на прогретом helper-сервере. Поэтому по умолчанию читается только основной регистр `ТоварыНаСкладах`. Контрольные регистры включай только если пользователь просит сверку, есть сомнение в результате или обнаружено расхождение:

```powershell
.\onec_integration\query_stock_server.cmd -Item "<код или часть наименования>" -Warehouse "<секция или склад>" -Control
```

Для списка до 30 позиций не запускай 30 отдельных COM-процессов. Передай массив в один запрос helper-серверу:

```powershell
.\onec_integration\query_stock_server.cmd -Item "<код1>" "<код2>" -Warehouse "<секция или склад>"
```

Закрепленные параметры:

- COM-коннектор: `V83.COMConnector`.
- `.env` с учетными данными: `C:\Users\dpd\Documents\Codex\1C_Diagnostics\.env`; пароль не читать вслух, не выводить и не копировать в проект.
- Python с pywin32: `C:\Users\dpd\Documents\Codex\1C_Diagnostics\.venv\Scripts\python.exe`.
- Основной сервер: `pz-sql1.pzmc.org:1541`; если DNS/FQDN не проходит, использовать fallback `pz-sql1:1541`.
- База: `UT_dev`, если пользователь явно не указал другую.
- Основной регистр фактического остатка: `ТоварыНаСкладах`.
- Контрольные регистры для сверки по флагу `--control`: `ПартииТоваровНаСкладах`, `ТоварыОрганизаций`.
- Основной ресурс количества: `Количество`.

Для ответа пользователю бери число из `summary` файла `onec_integration/reports/quick_stock_lookup.json`. Консоль Windows может искажать русские буквы, JSON сохраняется в UTF-8 и является приоритетным источником. Команда только читает 1С и не создает объектов.

На 2026-07-21 найдены локальный кэш IPS Viewer, основные таблицы `IMS_OBJECTS`, `IMS_OBJECT_ATTRS`, `IMS_RELATIONS`, `IMS_STORAGE` и способ чтения PDF через `IMS_STORAGE.F_FILEBODY`, но рабочая строка подключения к базе IPS еще не подтверждена. ## Правила разработки

- Сначала разберись в существующем слое и паттерне, затем меняй код точечно.
- Не ломай пользовательские Excel-форматы: импортеры должны быть терпимы к разным заголовкам и проблемным книгам.
- Для больших наборов данных избегай загрузки лишних таблиц в память; фильтрацию, сортировку и агрегацию по возможности оставляй в SQL.
- Новые бизнес-правила покрывай тестами в `tests/BlankDemandPlanner.Tests`.
- Для изменений расчета добавляй регрессионные тесты с понятными числами: потребность, НЗП, остаток, итог к закупке.
- Не удаляй накопленные справочные данные без явного решения пользователя. Если сущность уже участвовала в истории, предпочитай архивирование.
- UI должен оставаться рабочим инструментом для производства и снабжения: плотные таблицы, понятные команды, минимум декоративности.
- Сохраняй русскоязычные пользовательские термины: "Потребность", "Библиотека", "НСИ", "Остатки", "Расчет материалов", "Заявка", "В производстве".

## Обновления, версии и запуск ПО

- Все работы по опубликованным обновлениям, сборкам и версиям веди в `C:\Users\dpd\Documents\Заказ заготовок для ЦМО\publish\versions`.
- Для каждой опубликованной версии создавай отдельную папку `publish\versions\<version>`, где `<version>` совпадает с заголовком записи в `VERSION.md`.
- Не считай обновление завершенным, пока соответствующая папка в `publish\versions` не создана или явно не записано, почему публикация не выполнялась.
- После завершения любого обновления всегда открывай ПО "Заказ заготовок ЦМО" для пользовательской проверки.

## Thread close protocol

To prevent loss of project memory when a Codex thread disappears, every significant thread must finish with a checkpoint:

1. Update `SESSION_HANDOFF.md`: goal, completed work, changed files, verification, remaining risks and open questions.
2. Update `VERSION.md` when the work changes user-visible behavior, calculation, import, export, UI, data, docs, or published builds.
3. If a build or update is published, verify that `publish/versions/<version>` exists and matches the version name in `VERSION.md`.
4. If business rules, architecture, or long-term constraints changed, update `PROJECT_CONTEXT.md`.
5. If agent rules changed, update `AGENTS.md`.
6. If `git` is unavailable, `.git` is empty, or history cannot be read, record that explicitly in `SESSION_HANDOFF.md`.
7. If lost context is reconstructed, create `RECOVERY_YYYY-MM-DD[_range].md` with sources, limitations, reconstructed timeline, and next actions.

Minimum guard algorithm:

- start: read `AGENTS.md`, `PROJECT_CONTEXT.md`, `SESSION_HANDOFF.md`, `VERSION.md`, and latest `RECOVERY_*.md` if present;
- milestone: record user-significant results in `VERSION.md`;
- before final response: reconcile `VERSION.md`, `SESSION_HANDOFF.md`, verification, and published artifacts;
- after finishing an update: open the "Заказ заготовок ЦМО" application;
- final response: state what was verified and where the state was recorded.
