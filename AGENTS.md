# AGENTS.md

## Назначение проекта

Проект "Планирование ЦМО" автоматизирует определение того, какие материалы и заготовки нужно закупить и к какой дате, исходя из трех источников:

- библиотеки деталей и соответствующих им заготовок;
- текущей производственной потребности;
- остатков склада и НЗП из выгрузок 1С.

Приложение должно быть готово к постоянному развитию, накоплению производственной истории и работе с десятками тысяч деталей. При доработках нужно беречь масштабируемость, проверяемость расчетов и воспроизводимость импортов из Excel.

## Обязательные проектные документы

Каждый агент, работающий в этом репозитории, обязан читать и поддерживать:

- `AGENTS.md` - правила работы агентов и ключевые договоренности проекта.
- `PROJECT_CONTEXT.md` - бизнес-контекст, архитектура, доменная модель и текущие возможности.
- `SESSION_HANDOFF.md` - актуальное состояние последней сессии, нерешенные вопросы, следующие шаги.
- `VERSION.md` - журнал пользовательски значимых изменений и опубликованных сборок.

Перед изменением кода сначала прочитай эти файлы. После значимой доработки обнови `PROJECT_CONTEXT.md`, `SESSION_HANDOFF.md` и при необходимости `VERSION.md`. Если решение меняет правила работы агентов, обнови также `AGENTS.md`.

## Текущее приложение

Репозиторий содержит Windows WPF-приложение на .NET 8:

- `BlankDemandPlanner.Core` - сущности, enum-типы, интерфейсы и DTO/records.
- `BlankDemandPlanner.Data` - EF Core контекст, SQLite-схема, миграции, индексы и история изменений справочных сущностей.
- `BlankDemandPlanner.Services` - бизнес-логика: нормализация заготовок, проверка И-012, расчет закупочной потребности, конвертация единиц, поиск дублей.
- `BlankDemandPlanner.Infrastructure` - импорт Excel/1С/ПП/производственной библиотеки, экспорт отчетов Excel, резервные копии.
- `BlankDemandPlanner.UI` - WPF UI на MVVM с `CommunityToolkit.Mvvm`.
- `BlankDemandPlanner.Tests` - xUnit/FluentAssertions тесты доменных сервисов, импортов и ViewModel.

Основная пользовательская база приложения хранится в SQLite в `Данные для работы\BlankDemandPlanner.db` внутри рабочего каталога проекта, чтобы ручные правки библиотеки и НСИ сохранялись между обновлениями ПО. При первом запуске после перехода база копируется из старого `%LOCALAPPDATA%\BlankDemandPlanner\BlankDemandPlanner.db`, если новая еще не создана. Логи пишутся в `%LOCALAPPDATA%\BlankDemandPlanner\Logs`; резервные копии - в `%LOCALAPPDATA%\BlankDemandPlanner\Backups`.

## Ключевые бизнес-правила

- IPS - основной идентификатор изготавливаемой детали.
- УТ/1С-код - основной идентификатор складской/номенклатурной позиции заготовки.
- Связь `Part -> CanonicalBlank` задает норму расхода заготовки на деталь.
- У детали может быть несколько активных связей, но только одна активная основная связь.
- Расчет берет последнюю партию потребности и последний снимок склада, если явно не передан другой снимок.
- Заявка должна отображать список деталей и соответствующих заготовок со сроками потребности.
- На первом этапе расчетная дата закупки считается как `дата потребности - 30 дней`; позже срок должен браться из библиотеки данных/вкладки расчетных сроков изготовления и поставки.
- Остатки склада вычитаются по алиасам заготовок 1С.
- Строки остатков 1С, где код совпадает с IPS детали из потребности и единица измерения `шт`, трактуются как НЗП. НЗП вычитается из количества деталей до расчета потребности в заготовках.
- Для сопоставления цифровых IPS/кодов 1С используй 11-значный ключ с ведущими нулями: `1802132` должен совпадать с `00001802132`; буквенно-цифровые УТ-коды вроде `УТ000004539` сравниваются как отдельные УТ-коды.
- Для сопоставления деталей приоритет имеет IPS, для сопоставления заготовок - УТ/1С-код.
- В ручном поиске и подсказках пользователь может вводить текст заглавными или строчными буквами; кириллица должна искаться без учета регистра. Для кодов и обозначений дополнительно учитывай похожие русские/латинские буквы, например `01-р014` должен находить `01-P014`.
- Поиск в окнах должен понимать пользовательский ввод с ведущими нулями и составные запросы по нескольким колонкам: `00001414993` должен находить `1414993`, а `04.067.02.003 Гайка плоская` должен находить строку, где обозначение и наименование разнесены по разным полям.
- В поиске НСИ/1С и библиотечных подсказках русская `д` перед размером должна пониматься как диаметр `D`: `Круг д60 сталь 20` должен находить `Круг D60 Сталь 20`.
- Дубли НСИ считать по физическому ключу заготовки, а не по одному материалу или произвольной нормализованной строке имени. Базовый ключ: вид заготовки, единица, материал, ГОСТ материала, ГОСТ сортамента и точные размеры; если размеров нет, допускается сравнение по полному имени, но не по одной марке материала.
- При автодобавлении деталей из вкладки "Планирование" / источника МСК в Библиотеку принимать только нормальный цифровой IPS: 7 или 11 цифр. Короткие числа вроде `463`, `-`, текстовые обозначения, `ZAGOTOVKA...` и прочие не-IPS строки не должны создавать карточки деталей.
- Для НСИ пользовательское наименование заготовки по УТ/IPS-коду должно актуализироваться из реальной 1С УТ. Если Excel и 1С расходятся, в окне НСИ показывать наименование из 1С, а Excel считать только исходным источником атрибутов. Сверка выполняется при первом открытии НСИ в сеансе и при ручном нажатии верхней кнопки `Обновить данные 1С`.
- В редакторе НСИ выпадающий список `Марка материала` должен строиться только по активным строкам НСИ, то есть по активным `BlankAlias` с активной канонической заготовкой; материалы из библиотечных/канонических записей без активной позиции НСИ показывать нельзя. При выборе/вводе существующей марки материала ГОСТ материала можно подставлять автоматически из активной НСИ по самому частому совпадению, но пользовательский ручной ввод нельзя перетирать. ГОСТ сортамента можно автоматически подставлять по выбранному виду заготовки из активной НСИ, кроме вида `Покупная`; поле остается редактируемым.
- Длинномерные заготовки по умолчанию должны работать в `пог. м`; штучные, покупные, литые и листовые позиции - по фактической единице, если нет отдельного правила.
- Для удобства пользователя норма расхода длинномерных заготовок может вводиться и отображаться в `мм`, но хранение, расчет материалов, заявки и комплектации 1С должны использовать учетную единицу `пог. м`: `62 мм` = `0,062 пог. м`. Остатки длинномерных заготовок в НСИ показывай в `мм`.
- Несовместимые единицы измерения не должны молча пересчитываться. Сейчас пересчет разрешен только при полном совпадении единиц.
- Повторный импорт того же файла потребности должен обновлять существующую партию, а не создавать дубль.

## Авторизация и права доступа

- В WPF-приложении вход обязателен: если пользователей нет, сначала создается администратор через окно первичной настройки; далее основное окно открывается только после успешного входа.
- Пароли никогда не хранить в открытом виде. Для текущего WPF использовать bcrypt (`BCrypt.Net-Next`) с work factor не ниже 10; закрепленное значение - 12. В базе хранить только хэш.
- Неудачные попытки входа логировать в `AuthLoginAttempts`; включать защиту от brute-force на вход: не более 5 неудачных попыток за 15 минут для одного логина.
- Администратор имеет полный доступ, может создавать пользователей, генерировать и сбрасывать пароль, назначать права `Чтение`/`Редактирование` по вкладкам. Обычный пользователь в `Настройках` может менять только собственный пароль.
- Для будущего серверного режима обязательно: HTTPS only; cookie только с флагами `Secure`, `HttpOnly`, `SameSite=Strict`; CSRF-защита при cookie-сессиях; backend-валидация входных данных; rate limiting на `/login` и `/register`; логирование неудачных входов; endpoint сброса пароля только для администратора. Не переносить доверие к правам в клиентский UI: backend должен проверять права на каждую операцию записи.

## Оперативные запросы остатков 1С

Если пользователь спрашивает текущий остаток конкретной детали/номенклатуры в 1С УТ, сначала используй прогретый read-only helper-сервер, а не Excel и не повторное обследование метаданных:

```powershell
Invoke-RestMethod -Uri "http://127.0.0.1:8765/health"
.\onec_integration\start_stock_lookup_server.cmd
.\onec_integration\query_stock_server.cmd -Item "<код или часть наименования>" -Warehouse "<секция или склад>"
```

Если helper-сервер не запущен, первый старт может занять около 50 секунд на открытие COM-соединения. После прогрева запросы должны идти заметно быстрее, так как COM-подключение уже открыто. Прямой cold-start fallback:

```powershell
.\onec_integration\lookup_1c_stock.cmd "<код или часть наименования>" "<секция или склад>"
```

Целевой регламент скорости: один запрос или пакет до 30 строк должен готовиться максимально коротким путем, ориентир - до 30 секунд на прогретом helper-сервере. Поэтому по умолчанию читается только основной регистр `ТоварыНаСкладах`. Контрольные регистры включай только если пользователь просит сверку, есть сомнение в результате или обнаружено расхождение:

```powershell
.\onec_integration\query_stock_server.cmd -Item "<код или часть наименования>" -Warehouse "<секция или склад>" -Control
```

Для списка до 30 позиций не запускай 30 отдельных COM-процессов. Передай массив в один запрос helper-серверу:

```powershell
.\onec_integration\query_stock_server.cmd -Item "<код1>" "<код2>" -Warehouse "<секция или склад>"
```

Закрепленные параметры:

- COM-коннектор: `V83.COMConnector`.
- `.env` с учетными данными: `C:\Users\dpd\Documents\Codex\1C_Diagnostics\.env`; пароль не читать вслух, не выводить и не копировать в проект.
- Python с pywin32: `C:\Users\dpd\Documents\Codex\1C_Diagnostics\.venv\Scripts\python.exe`.
- Основной сервер: `pz-sql1.pzmc.org:1541`; если DNS/FQDN не проходит, использовать fallback `pz-sql1:1541`.
- База: `UT_dev`, если пользователь явно не указал другую.
- Основной регистр фактического остатка: `ТоварыНаСкладах`.
- Контрольные регистры для сверки по флагу `--control`: `ПартииТоваровНаСкладах`, `ТоварыОрганизаций`.
- Основной ресурс количества: `Количество`.

Для ответа пользователю бери число из `summary` файла `onec_integration/reports/quick_stock_lookup.json`. Консоль Windows может искажать русские буквы, JSON сохраняется в UTF-8 и является приоритетным источником. Команда только читает 1С и не создает объектов.

## OData 1С УТ

Дополнительно проверен read-only OData endpoint:

```text
http://pz-sql1/ut_dev/odata/standard.odata/
```

Он опубликован отдельно от COM, требует Basic-авторизацию учетной записью 1С из внешнего `.env` и предоставляет `Catalog_Номенклатура`, `Catalog_Склады`, `AccumulationRegister_ТоварыНаСкладах` и функцию `Balance(Condition, Dimensions, Period)`. Подробный замер и решение смотри в `onec_integration/docs/ODATA_STOCK_ANALYSIS.md`.

Для оперативного одиночного запроса при прогретом helper-сервере пока оставляй основным `query_stock_server.cmd`: он возвращает код, наименование, склад и количество без отдельного кэша GUID. Встроенная синхронизация ПО сначала пробует OData-скрипт `onec_integration/tools/sync_stock_sections_odata.py` с коротким лимитом времени, а при ошибке или сомнительном результате автоматически переходит на COM. Запись документов 1С через OData в контуре остатков не выполнять.

## Перемещение товаров 1С

Для создания документа 1С `ПеремещениеТоваров` используй OData-скрипт `onec_integration/tools/create_goods_transfer_odata.py`; учетные данные брать только из внешнего `.env`, пароль не выводить. Запись разрешается только при явном `--allow-write`, документ всегда создается непроведенным (`Posted=false`) и не проводится без отдельного прямого указания пользователя.

Проверенный пробный маршрут от 2026-08-03:

```powershell
C:\Users\dpd\Documents\Codex\1C_Diagnostics\.venv\Scripts\python.exe .\onec_integration\tools\create_goods_transfer_odata.py --allow-write --empty-trial --source "44 секция НЗП (незавершенное производство)" --target "Детали МУ в обработке на стороне" --organization "СТП ПЗМЦ АО" --comment "Пробное перемещение ПО Планирование ЦМО; без проведения; без строк товаров"
```

Если пользователь не указал номенклатуру и количество, не добавляй строки товаров по догадке. Пустой документ допустим только как явно пробный `--empty-trial`; для реального перемещения нужны строки `--item "<УТ/IPS/код>" "<количество>"`. ## Отчеты 1С УТ

Для отчетов по движениям 1С УТ используй read-only OData-скрипт `onec_integration/tools/build_onec_ut_reports_odata.py`; учетные данные брать только из внешнего `.env`, запись в 1С не выполнять. Период передавай явно:

```powershell
C:\Users\dpd\Documents\Codex\1C_Diagnostics\.venv\Scripts\python.exe .\onec_integration\tools\build_onec_ut_reports_odata.py --start 2026-08-01 --end 2026-08-04
```

Скрипт формирует JSON `onec_integration/reports/onec_ut_period_reports.json` и CSV-файлы для двух отчетов:

- `transfers_from_44_to_production_or_paint`: строки `Document_ПеремещениеТоваров.Товары` за период, где отправитель `44 секция НЗП (незавершенное производство)` (`ba59fa3b-e5f1-11eb-860c-0cc47adb8d79`), получатель `1 секция (ПЗМЦ) только для производственных целей` (`04287e48-1b7d-11e8-8277-00155d586401`) или `Покраска ТМЦ` (`e1228c71-3243-11f1-866c-0cc47adb8d79`). В строках выводить документ, дату, склад-получатель, код/артикул/номенклатуру, единицу и количество; итог группировать по складу-получателю и номенклатуре.
- `assembly_materials_44_raw_to_details`: строки `Document_КомплектацияНоменклатуры.Комплектующие` за период, где склад документа `44 секция НЗП (незавершенное производство)`. Это отчет списания из "сырья" в детали: выпуск детали берется из реквизитов документа `Номенклатура/Количество`, списываемый материал - из табличной части `Комплектующие`.

По умолчанию включай только проведенные документы (`Posted=true`), потому что они отражают фактические движения и списание. Флаг `--include-unposted` использовать только для диагностики черновиков или когда пользователь явно просит включить непроведенные документы.

Вкладка `Отчет` располагается сразу после `Планирование` и формирует управленческий отчет механического цеха за выбранный период. План выпуска бери из последней потребности за период, факт выпуска - из read-only отчета 1С `transfers_from_44_to_production_or_paint` по перемещениям из 44 секции на `1 секция (ПЗМЦ) только для производственных целей` и `Покраска ТМЦ`, OEE/загрузку - из рассчитанного плана вкладки `План`, персонал - из API ПО "Производство" при доступности. Простои, ремонты, аварии, ФОТ, материалы и запчасти оставляй ручными полями: если точных данных нет, не выдумывай цифры и явно показывай, что данные не внесены.

## Правила разработки

- Сначала разберись в существующем слое и паттерне, затем меняй код точечно.
- Не ломай пользовательские Excel-форматы: импортеры должны быть терпимы к разным заголовкам и проблемным книгам.
- Для больших наборов данных избегай загрузки лишних таблиц в память; фильтрацию, сортировку и агрегацию по возможности оставляй в SQL.
- Новые бизнес-правила покрывай тестами в `tests/BlankDemandPlanner.Tests`.
- Для изменений расчета добавляй регрессионные тесты с понятными числами: потребность, НЗП, остаток, итог к закупке.
- Не удаляй накопленные справочные данные без явного решения пользователя. Если сущность уже участвовала в истории, предпочитай архивирование.
- UI должен оставаться рабочим инструментом для производства и снабжения: плотные таблицы, понятные команды, минимум декоративности.

- Во всех таблицах копирование должно брать только фактически выделенные ячейки, без подтягивания всей строки и без заголовков. Нельзя полагаться на стандартное копирование `DataGrid`, если оно копирует `SelectedItem`/строку вместо `SelectedCells`.
- Удаление НСИ через контекстное меню должно быть обратимым через общую команду `Отменить`: перед физическим удалением сохраняй снимок алиасов, канонических заготовок, карт применяемости, ссылок остатков и ссылок расчетов, чтобы случайно удаленную позицию можно было восстановить в рабочий список.

## Синхронизация остатков 1С

Синхронизация остатков в ПО "Планирование ЦМО" встроена через WPF-сервис `OneCStockSyncService`: сначала пробуется read-only OData-контур `onec_integration/tools/sync_stock_sections_odata.py`, затем резервный read-only Python/COM-контур `onec_integration/tools/sync_stock_sections.py`. Оба пути создают обычный `StockSnapshot`, Excel-импорт остатков сохранен как технический резервный канал, но верхняя рабочая кнопка должна вести пользователя к обновлению из 1С. После успешной синхронизации остатков эта же кнопка запускает пакетную сверку активных наименований НСИ с реальной 1С УТ.

Закрепленные складские правила:

- остаток ЦМО / НЗП брать суммой по `44 секция НЗП (незавершенное производство)` и `Детали МУ в обработке на стороне`;
- складской остаток для производственных целей брать суммой по `1 секция (ПЗМЦ) только для производственных целей`, `Покраска ТМЦ`, `ТМЦ по проекту ФРП`, `ТМЦ для проверки ОТК`, `ТМЦ для временного хранения ЦСТС`, `ТМЦ для временного хранения ЦМО`;
- расчет материалов должен вычитать заготовки по активным УТ/алиасам из закрепленных групп "Склад" и "НЗП/ЦМО"; НЗП деталей вычитать отдельно по IPS только по закрепленной группе "НЗП/ЦМО";
- запись документов 1С в рамках синхронизации остатков не выполнять.

## Обновления, версии и запуск ПО

- Все работы по опубликованным обновлениям, сборкам и версиям веди в `C:\Users\dpd\Documents\Заказ заготовок для ЦМО\publish\versions`.
- Для каждой опубликованной версии создавай отдельную папку `publish\versions\<version>`, где `<version>` совпадает с заголовком записи в `VERSION.md`.
- Не считай обновление завершенным, пока соответствующая папка в `publish\versions` не создана или явно не записано, почему публикация не выполнялась.
- После завершения любого обновления всегда открывай ПО "Планирование ЦМО" для пользовательской проверки.
- При каждом опубликованном обновлении сохраняй пользовательское название ПО `Планирование ЦМО` в заголовке окна, метаданных сборки и ярлыке меню Пуск; заголовок системного окна должен быть без версии: `Планирование ЦМО`; после публикации создавай или обновляй ярлык `Планирование ЦМО.lnk` в `%APPDATA%\Microsoft\Windows\Start Menu\Programs`, указывающий на актуальный exe из папки опубликованной версии.
- В верхнем левом углу рабочей панели сохраняй только графический логотип `PZMC_1.png`. Не добавляй рядом с логотипом версию ПО, slug версии или текстовое название приложения.
- В левой навигации не включай скроллинг и не обрезай названия вкладок; пункт `Расчет материалов` должен помещаться полностью.
- Запуск в производство из вкладки `Планирование` должен создавать в 1С документ `КомплектацияНоменклатуры` непроведенным (`Posted=false`), пока пользователь отдельно не утвердит проведение документов и складское списание.
- Доступное количество для запуска в производство считай по остаткам материала из группы `Склад` плюс `НЗП/ЦМО`, включая `44 секция НЗП (незавершенное производство)`, потому что комплектация создается через 44 секцию. Для закупочного расчета то же правило применяется только к остаткам самих заготовок по УТ/алиасам; НЗП деталей по IPS вычитается отдельной логикой.
- Для запуска в производство заготовок в `пог. м` учитывай рез 5 мм между деталями: компонент 1С = `норма * количество + 0,005 * (количество - 1)`, доступное количество запуска также ограничивается этой формулой. Комментарий запуска должен быть коротким и редактируемым: только `Создано ПО Планирование` и пары `№ станка; количество`, без IPS, детали, расхода, проектов/ПС, дат и текста `не проведено`.
- Режим `Запуск по 1 шт` во вкладке `Планирование` создает несколько непроведенных комплектаций 1С по одной детали каждая и распределяет их по строкам дефицита/№ станков сверху вниз. Комментарий каждой карты строится как `Создано ПО Планирование <№ станка>; 1 шт`, где первая часть может быть отредактирована пользователем в окне запуска.
- В комплектации 1С закреплены реквизиты: ответственный `Аракелян Армен Седракович` (`ce72f423-5baf-11ef-864f-0cc47adb8d79`), подразделение всегда `Цех механической обработки` (`14c61f15-1510-11f0-8660-0cc47adb8d79`). Единицы измерения для выпуска и комплектующих брать из `ЕдиницаХраненияОстатков_Key`, затем `ЕдиницаДляОтчетов_Key`; не использовать `БазоваяЕдиницаИзмерения_Key` как основной источник, чтобы не получить `<Объект не найден>` в форме 1С.
- Команда `Услуги на стороне` во вкладке `Планирование` должна брать строки только из последнего НЗП `44 секция НЗП (незавершенное производство)` в `шт` и создавать один непроведенный документ 1С `ПеремещениеТоваров` из 44 секции в `Детали МУ в обработке на стороне`. Вид услуги выбирается из закрепленного списка: `Хим окс`, `Азотирование`, `Шпоночный паз`, `Термообработка`; пользователь может отметить детали вручную или вставить список IPS/кодов. В списке выбора услуг один IPS/код показывается одной строкой с общим количеством НЗП, без повторения под разные проекты; галочка `Только в потребности` оставляет только позиции с реальными строками последней потребности. Заявка на услугу и автоматический комментарий раскрывают выбранное количество по строкам последней потребности: `ПС`, `№ станка`, количество и исходная дата потребности; если выбранного количества больше, чем потребность по этому IPS, остаток добавляется строкой `на склад` в `ПС` и `№ станка`. Комментарий формировать коротко по принципу запуска в производство: `Услуги на стороне: <вид услуги> <№ станка>; <кол-во> шт`, оставляя ручное редактирование. Кнопка `Сформировать заявку` в этом окне создает Excel-бланк с колонками `№`, `ПС`, `№ станка`, `Код IPS`, `Номенклатура`, `Ед. измерения`, `Кол-во`, `Обоснование`, `Дата потребности`, `Примечание`, `Цена, руб`, `Стоимость, руб`; дата в заявке считается от даты формирования файла: `Азотирование` +10 дней, остальные услуги +7 дней. Если расчетная дата услуги позже исходной даты потребности, дату и `СРОЧНО!` в примечании выделяй красным жирным.
- Для минимизации списка `Услуги на стороне` каждая карточка детали в Библиотеке хранит признаки услуг: `Азотирование`, `ТО`, `Хим. окс`, `Шпон паз`. В окно услуг попадают только детали из 44 секции НЗП, у которых отмечена хотя бы одна услуга, а выбранный вид услуги дополнительно фильтрует список по соответствующей галочке.
- Во вкладке `Подбор заготовок` фильтр `С положительным остатком` должен брать данные только из последнего сохраненного снимка остатков и показывать подходящие заготовки с количеством больше 0 по нормализованному УТ/IPS-коду.

## Thread close protocol

To prevent loss of project memory when a Codex thread disappears, every significant thread must finish with a checkpoint:

1. Update `SESSION_HANDOFF.md`: goal, completed work, changed files, verification, remaining risks and open questions.
2. Update `VERSION.md` when the work changes user-visible behavior, calculation, import, export, UI, data, docs, or published builds.
3. If a build or update is published, verify that `publish/versions/<version>` exists and matches the version name in `VERSION.md`.
4. If business rules, architecture, or long-term constraints changed, update `PROJECT_CONTEXT.md`.
5. If agent rules changed, update `AGENTS.md`.
6. If `git` is unavailable, `.git` is empty, or history cannot be read, record that explicitly in `SESSION_HANDOFF.md`.
7. If lost context is reconstructed, create `RECOVERY_YYYY-MM-DD[_range].md` with sources, limitations, reconstructed timeline, and next actions.

Minimum guard algorithm:

- start: read `AGENTS.md`, `PROJECT_CONTEXT.md`, `SESSION_HANDOFF.md`, `VERSION.md`, and latest `RECOVERY_*.md` if present;
- milestone: record user-significant results in `VERSION.md`;
- before final response: reconcile `VERSION.md`, `SESSION_HANDOFF.md`, verification, and published artifacts;
- after finishing an update: open the "Планирование ЦМО" application;
- final response: state what was verified and where the state was recorded.
